# 设计：启动服务不再清空终端日志（会话内保留）

- 日期：2026-08-18
- 状态：已确认（用户批准方案 A）
- 目标版本：0.1.3（下一 patch）

## 背景与动机

用户需要反复进入「查看日志」页面（`/terminal`）核对服务启动/运行日志。当前每次启动/重启服务都会清空日志历史：

- `useAppStore.startFlow()` 在流程开始前执行 `set({ logs: [], error: null })`
- `useAppStore.reset()`（重试/重新启动按钮调用）同样重置 `logs: []`

导致「重试」「重新启动」「停止后再启动」以及服务失败/停止后重新进入 Terminal 页自动触发 `startFlow()` 时，上一轮日志全部丢失，无法对照排查。

用户已确认采用**会话内保留**：日志保留到应用窗口关闭为止（内存态），不做磁盘持久化。

## 方案（用户批准的方案 A）

改动集中在 `src/store/useAppStore.ts`（日志上限/截断/保留逻辑）与 `src/pages/Terminal.tsx`（自动滚动依赖修正，见 3.2），无 Rust 改动。

### 1. `startFlow()`：不再清空日志

- `set({ logs: [], error: null })` → `set({ error: null })`
- 若 `get().logs.length > 0`，先追加一条 system 分隔线：`────── 重新启动服务 ──────`，再开始新流程，使多次运行的历史在视觉上可分辨

### 2. `reset()`：仅重置状态机

- 去掉 `logs: []`，保留 `phase/url/error/serviceRunning/childRunning` 的现有重置
- 该函数只负责把状态机复位到可重新启动的状态，不负责清空日志

### 3. `appendLog()`：上限保护与截断提示

- 新增模块常量 `MAX_LOGS = 3000`
- 追加后若 `logs.length > MAX_LOGS`：**丢弃最旧日志，保留最近 `MAX_LOGS - 1` 条真实日志**，顶部放一条 system 提示 `（历史日志过长，已截断早期内容）`，总量恒为 `MAX_LOGS`
- 关键点：保留的是**最新**日志（窗口尾部），绝不是窗口头部——初版实现误用 `slice(0, MAX_LOGS-1)` 会丢掉刚追加的最新一条，已被审查发现并修正
- 截断提示为"重建式固定"：截断期间顶部始终恰好存在一条（每次截断重建 id 与时间戳），不会堆积多条

### 3.1 `Terminal.tsx`：自动滚动依赖修正

- 日志达到 `MAX_LOGS` 后 `logs.length` 恒定不变，原自动滚动 effect 依赖 `[logs.length]` 不再触发
- 改为依赖最后一条日志的 id：`[logs.at(-1)?.id]`，每次追加仍滚动到底部

## 行为影响

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 重试 / 重新启动 | 日志清空 | 旧日志保留，分隔线后开始新日志 |
| 停止后再启动 | 日志清空 | 「🛑 已停止」等历史保留 |
| 失败后重新进入 Terminal 页 | 自动重启并清空 | 自动重启但保留历史 |
| 窗口关闭 / 应用退出 | 日志丢失（内存态） | 同样丢失（会话内保留，已确认可接受） |

- Terminal 页空态（`logs.length === 0`）、`logs.map` 渲染无需改动；自动滚动依赖按 3.1 修正（依赖最后一条日志 id）
- `Launch.tsx` 不依赖 `logs`，无需改动
- 不做「清空日志」手动按钮（YAGNI，超出本次需求）

## 验证

1. 启动服务 → 停止 → 重新启动：Terminal 页能看到分隔线，分隔线前为上一轮日志
2. 制造启动失败（error）→ 点「重试」：失败日志保留在分隔线前
3. 服务运行中反复进出「查看日志」页：日志持续累积、不丢失
4. 超长日志（>3000 条）时只保留最近 3000 条（**最新一条必须保留**）、顶部出现且仅出现一条截断提示
